# 缓存语义

## 1. 缓存目录布局

启用 `-cache <dir>` 后，缓存为本地目录：

```
<dir>/
  VERSION        # 单行文本：缓存格式版本，当前 "1"
  results/
    <64 位十六进制 key>   # 每条结果一个不可变文件
    .tmp-<random>         # 原子写入的临时文件（崩溃残留会被忽略）
```

## 2. 缓存键（只由内容与配置决定）

- 先算原始内容摘要：`rawHash = sha256(原始文件字节)`；
- 再算配置指纹：`fp = sha256(规范JSON{algorithm_version, cache_format,
  codec, compression_level})`；
- 最终 `key = sha256(rawHash + "|" + fp)`。

键中**不包含**源路径、机器名、时间戳、并行度、超时、缓存目录本身等任何运营性
信息，所以跨机器、跨目录、换并行度都能命中同一缓存。

## 3. 何时命中 / 何时失效

- 命中：键存在且条目完整性校验通过。构建报告会把该资源标记为 `cached`，否则
  标记为 `processed`（link 虚拟资产标记为 `link`）。
- 内容变化 → `rawHash` 变化 → 新键，旧条目不影响新构建。
- 任一**输出相关**配置变化（codec、压缩级别）→ 指纹变化 → 全部 miss。
- 算法/缓存格式升级：提升 `config.AlgorithmVersion` 与
  `cache.CacheFormatVersion` 后，`cache.Open` 读到不匹配的 `VERSION` 戳会
  **整体清空** `results/` 并写入新戳，旧格式条目绝不可能被新代码读到。

## 4. 完整性与原子性（防部分写入/损坏）

每个条目文件的二进制帧：

```
"TXC1" | uint32 meta长度 | meta JSON
       | uint64 raw长度   | raw 字节
       | uint64 encoded长度 | encoded 字节
```

`meta` 记录路径、类型、两段长度与 `raw/encoded` 的 SHA-256。读取时校验：

1. 魔数；2. 所有长度字段不越界；3. JSON 可解析；4. 无尾随字节；
5. 长度与实际一致；6. 两段负载哈希与 meta 一致。

任一条不满足即判定 `cache.ErrCorrupt` 并**立即删除**该条目；构建随后回退为
重新处理（自愈），最终包仍与干净重建逐字节一致。临时文件 `.tmp-*` 不以键名
存在，永远不会被当作查询结果。

写入走“同目录唯一临时文件 → 写全 → fsync → rename → fsync 目录”，因此：
`cache.Open` 还会清扫上次崩溃/中断遗留在 `results/` 下的 `.tmp-*` 文件，
避免磁盘空间泄漏。

- 读到的条目要么完整、要么不存在；
- 构建被取消/断电不会产生半截“有效”条目；
- 资源包同理：先在内存组装完整包，再原子 rename 发布，构建失败或取消时目标
  路径不会留下/覆盖出半成品（原包在失败构建后保持不变）。

## 5. 容量上限

`-max-cache N`（`Options.MaxCacheBytes`）在每次成功构建后尽力执行一次淘汰：
按最旧修改时间、再按键名字典序确定性地删除条目，直到总量 ≤ N。≤0 表示不限。

## 6. 增量与全量等价

增量构建只对内容/配置变化的资源重新编码，其余直接取缓存；由于 blob id 只取决于
编码后内容，且包内所有集合都按稳定排序输出，**增量包与全量重建包逐字节一致**
（有自动化测试断言）。
